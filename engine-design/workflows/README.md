# Harness execution contract

The workflows are harness-neutral work packets, not a pretend autonomous coding agent. `tools/workflow.py plan text` prints phases; `packet text I0` emits the next role assignment. The code harness executes the tasks, implements tests, schedules separate reviewer sessions and supplies evidence. This chat has not executed those implementation phases.

For each phase, an Explore session verifies sources and delivers a bounded evidence map first. An implementation session makes one scoped change set. A verifier session runs the cumulative tests at that exact candidate revision. Two fresh review sessions separately examine model semantics and systems/security; neither may be the implementer or verifier session. Parallel independent reviews are appropriate after the candidate is frozen. Record run IDs, reviewed SHA, report hashes and unresolved findings. Assign a repair to its responsible role and repeat affected tests/reviews; do not ask the operator to adjudicate C++ correctness.

Use one integration branch and an isolated worktree. At the code-harness handoff, fetch `design/dg-engine-20261019`, add a worktree for it when not already checked out, and preserve every other branch/worktree/dirty file. Reconcile main drift without merging unrelated research lineage. After each passing implementation phase, commit its evidence pointer and create an annotated `dg-engine/implementation/<run-id>/<phase>` tag. A tag is never moved. Push only the named branch and its exact tags. Keep raw large traces in the declared evidence store with checksummed pointers, not silently omitted logs.

The stage checker takes `check text I2 receipt.json --evidence-dir <bank> --commit <tested-sha>`. The harness must independently derive `--commit` from `git rev-parse HEAD`, require a clean source worktree and check that prerequisite receipts refer to ancestors. The utility verifies the receipt structure, workflow/requirement hashes, cumulative test IDs, artifact bytes and review record separation. It does not authenticate people, execute the engine, certify expertise, inspect Git ancestry, or prove that a log describes a truthful measurement. Those remain verifier/reviewer responsibilities, named rather than disguised as automated guarantees.

## Receipt format

A receipt is JSON with `schema:1`, `kind:"engine-phase-evidence"`, `flow`, `phase`, `commit` (40 hex), `workflow_sha256` and `requirements_sha256` (canonical JSON hashes), distinct nonempty `implementer_run` and `verifier_run`, `blockers:[]`, `prerequisites` (phase + banked receipt path, recursively validated), `artifacts` (relative path + SHA-256), `tests` (ID, status PASS, executed >0, failed/errors/skipped all zero, log path), and two `reviews` (scope model/systems, distinct run ID, status PASS, same commit, report path). All referenced logs/reports must exist in artifacts. For I5 include `nodes` equal to the frozen eight-node set. Bank binary/source-lock/coverage artifacts alongside the receipt and link them from test logs.

`workflow.py hashes text` prints the two canonical hashes needed in the receipt. Canonical JSON ignores whitespace but not values, ordering of arrays or fields. A modified workflow invalidates older gate records; document and rerun the affected baseline instead of silently editing a passing receipt. Non-PASS status, zero tests, any skipped mandatory test, stale commit, altered evidence, absent review or enabled-image attempt fails closed.

## Independent image workflow

`plan image` and `packet image M0` expose the image plan. `check image ...` always refuses because the manifest is disabled. This does not block planning, but prevents a gate utility from treating image implementation as authorized. IMAGE-01/02 compare processor and mmproj/source contracts; IMAGE-03/04 are future HF-versus-native embedding/KV and mixed-prompt tests; IMAGE-05 is future image-plus-full-text regression and distribution qualification. No image-capable engine code is supplied.
