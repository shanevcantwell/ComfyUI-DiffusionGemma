## Headline

0.5.0 passed its live functional gate four times and is still not shippable. The gate (#163) was sound and caught real bugs unit tests missed — but it tested live mechanics only and never checked branch/version integrity. When the operator finally inspected that dimension by hand (session b26cb78e), main, pre-0.5.0-release, and the already-shipped release/0.4.1 were found diverged into a three-way sibling fork since v0.4.0, with partially-ungated content on main. The release candidate is not a clean branch. Compounding this, the declared package version never moved off 0.4.0, and the operator's own closing read — "0.5.0 being just auto-round is not really what we were aiming for" — flags a scope-vs-intent gap on top of the hygiene gap.

## What actually went wrong (root-cause themes)

Theme 1 — One defect class, three manifestations. The load-path device-placement/VRAM-management defect was not a single bug; it recurred as the release chased it across branches:
- #173 — quant='none' did a full CPU load + unconditional .to("cuda") after device_map="auto" was dropped at dd2767c. OOM on any <53 GiB card. Caught by gate RUN 1.
- #183 — same defect class in the quant='autoround' path: no placement budget, overflows VRAM, runs ~10× slower than bf16. Caught by the operator in the field, not the gate — it vetoed a green "GO."
- #187 — same family again: RuntimeError: tensors on different devices in the split encoder/denoiser path under whole-fit INT4. Filed after #183's fix merged.

The corrective ("load should be load" — one unified load_kwargs shape, delete per-quant placement divergence, PR #185) is the right shape, but it arrived only after the third instance. The enforcement surface that would have caught this class up front did not exist.

Theme 2 — The live gate worked, and its blind spots are the lesson. #163 was born (session 53f61c1d) directly from two field-failures that reached the operator (#147 broken fresh install, #162 live KV-cache crash). It immediately paid for itself: RUN 1 caught #173, RUN 2 caught #178/#179, and it enforced Opus-gate rigor (PR #177's first attempt was failed for a device_map/meta-assert contradiction). But three classes of defect slipped past it anyway — the autoround VRAM path (#183), the split encoder path (#187), the run-log dir contract (#189) — all found by operator hand-play. The gate's scenario battery did not cover the operator's actual workflow or branch state.

Theme 3 — GO/NO-GO thrash from an untested dimension. "0.5.0 mechanics are GO" was declared at RUN 3 (f40725d), vetoed hours later by #183, restored at RUN 4 (a68e29d), then undercut again by the branch-hygiene discovery. Each flip was honest given what each actor tested — but the oscillation is the symptom of a gate that measured one axis (live smoke) while the release depended on two (live smoke and branch integrity).

- Version never bumped. pyproject.toml still reads 0.4.0 on main HEAD; no v0.5.0 tag. Every "0.5.0 GO" was about mechanics, not a versioned artifact.
- Release work is stranded off main. All gate/#183/#189 work lives on pre-0.5.0-release / fix/*; main HEAD (e115a41) does not contain it. main also carries a commit the release branch lacks (7525300, #162/#166) → genuine two-way merge, not a fast-forward.
- Shipped ≠ main. What's live for users is release/0.4.1, a sibling fork sharing only the v0.4.0 merge-base with the other two. Operator: "Shipped is actually 0.4.1, so that's not helping confidence."
- Two direct-pushes to protected main (handoffs 9ecb696, e115a41) under session-limit pressure — self-reported as branch-protection bypasses, not silent. A recurring practice worth a durable fix (handoff-landing shouldn't require it).
- Milestone "0.5.0" due_on (07-29) predates its own created_at (07-30) — overdue at birth.
- Scope-vs-intent gap. Operator: "0.5.0 being just auto-round is not really what we were aiming for" — the release's delivered surface is narrower than the felt target.
